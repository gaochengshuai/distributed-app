# Payment Service 业务逻辑说明

## 概述

本服务实现了完整的贷款业务流程，包括放款（Withdraw）、还款（Repayment）和对账（Reconciliation）三大核心模块。

## 核心业务流程

### 1. 放款流程（Withdraw）

#### 1.1 正常流程
```
用户发起提款申请 
→ 参数校验（AutoCheckReqFilter）
→ 加载上下文（LoadContextFilter）
→ 防重检查（IdeFilter）
→ 判断是否需要人工审核
→ 借据定价（利率、费用）
→ 计算手续费
→ 创建贷款登记记录
→ 根据放款模式创建支付订单
→ 调用支付网关
→ 支付成功：生成借据和还款计划
→ 支付失败：更新订单状态，支持重提
```

#### 1.2 异常处理

**场景1：支付网关调用失败**
- 不生成借据和还款计划
- 更新支付订单状态为失败（F）
- 核心账务未生成
- 用户可在页面点击"重提"按钮重新发起

**场景2：借款创建入账异常**
- 支付已成功，但后续保存数据异常
- 订单状态保持为"支付中"（J）或恢复原状
- 借据不落地
- 通过异步对账任务或人工干预修改状态

### 2. 还款流程（Repayment）

#### 2.1 正常流程
```
用户发起还款请求
→ 查询还款计划
→ 计算应还总额
→ 创建还款订单
→ 调用支付网关扣款
→ 支付成功：执行入账逻辑
  → 冲销引擎执行【费-息-本】顺序
  → 更新还款计划状态
  → 处理溢缴款
  → 创建还款记录
→ 支付失败：更新订单状态，不生成账务数据
```

#### 2.2 冲销引擎（费-息-本）

还款金额按以下顺序冲销：
1. **费用（Fee）**：优先冲销手续费、服务费等
2. **利息（Interest）**：其次冲销利息
3. **本金（Principal）**：最后冲销本金

#### 2.3 异常处理

**场景1：支付网关扣款失败**
- 不生成账务数据
- 更新订单状态为失败（F）
- 用户可重试

**场景2：核心入账异常**
- 支付已成功，但核心系统保存数据失败
- 订单状态保持为"支付中"（J）
- 创建对账异常记录
- 依赖对账文件，发现支付已成功但核心无记录时触发补账

**场景3：批量扣款部分失败**
- 异常挂起：借据标记为处理异常（E）
- 标记异常原因
- 重试机制：
  - 系统会在下一个批次自动重试
  - 特定重试任务再次尝试扣款
  - 连续失败的订单通过手动触发或线下处理

**场景4：金额不一致**
- **小额差异**（≤1元）：直接入账或拒绝提示
- **大额超额**（>100元）：超出部分记入溢缴款账户，用于下一期账单抵扣
- **中等差异**：生成差错账记录

### 3. 对账流程（Reconciliation）

#### 3.1 对账场景1：支付成功，核心未入账

**检测方式**：查询支付成功的订单，检查核心系统是否有对应记录

**处理方案**：
- **放款业务**：根据订单信息重新触发
  - 借据创建
  - 期供生成
  - 额度占用
  
- **还款业务**：调用入账接口重新执行
  - 冲销逻辑（费-息-本）
  - 生成分录
  - 更新期供状态

#### 3.2 对账场景2：核心已入账，支付未成功

**检测方式**：查询支付失败的订单，检查核心系统是否已有记录

**处理方案**：
1. 尝试撤销之前的入账操作
   - 生成反向分录
2. 将借据或订单回退到处理前的状态
3. 无法自动冲正时，标记为需贷后介入

#### 3.3 对账场景3：金额不一致

**检测方式**：比对支付金额和核心记账金额

**处理方案**：
- **小额差异**（≤1元）：自动记入损益科目，核销处理
- **大额差异**（>1元）：生成差错账，标记为人工处理

#### 3.4 定时对账任务

- **每日对账**：每天凌晨2点执行全量对账
- **每小时对账**：每小时执行增量对账（可选）

## API接口说明

### 放款相关

#### 1. 发起提款申请
```
POST /api/loan/withdraw
Body: WithdrawReq
Response: { success, orderId, message }
```

#### 2. 审核通过
```
POST /api/loan/approve/{loanRegId}
Response: { success, billNo, message }
```

#### 3. 重试提款（支付失败后重提）
```
POST /api/loan/retry/{orderId}
Response: { success, orderId, message }
```

### 还款相关

#### 4. 发起还款
```
POST /api/loan/repay?billNo={billNo}&amount={amount}&repayType={NORMAL|EARLY|OVERDUE}
Response: { success, orderId, message }
```

#### 5. 重试还款
```
POST /api/loan/repay/retry/{orderId}
Response: { success, message }
```

### 对账相关

#### 6. 手动触发对账
```
POST /api/loan/reconcile
Response: { success, message }
```

#### 7. 查询待处理的对账异常
```
GET /api/loan/reconcile/exceptions
Response: { success, data, count }
```

#### 8. 人工处理对账异常
```
POST /api/loan/reconcile/handle?exceptionId={id}&handleMethod={AUTO_RETRY|MANUAL|WRITE_OFF|REVERSAL}&result={result}
Response: { success, message }
```

## 数据库表结构

### 核心业务表

1. **cls_order** - 订单表
   - 存储所有放款和还款订单
   - 状态：U-未支付, J-支付中, S-成功, F-失败, E-异常, C-已撤销

2. **cls_loan_reg** - 贷款登记表
   - 存储贷款登记信息
   - 审核状态：U-待审核, A-审核通过

3. **cls_repay_plan** - 还款计划表
   - 存储每期还款计划
   - 状态：U-未还, P-部分还款, S-已还清, O-逾期

4. **cls_repay_record** - 还款记录表
   - 存储每次还款的详细记录
   - 支付状态：S-成功, F-失败, P-处理中

5. **recon_exception** - 对账异常表
   - 存储对账发现的异常
   - 状态：P-待处理, H-人工处理, R-已解决
   - 异常类型：PAY_SUCCESS_CORE_FAIL, CORE_SUCCESS_PAY_FAIL, AMT_MISMATCH

## 技术实现要点

### 1. 事务管理
- 使用`@Transactional`注解保证数据一致性
- 关键业务操作都在事务中执行

### 2. 异常处理
- 完善的异常捕获和日志记录
- 异常情况下数据回滚或标记为待处理

### 3. 对账机制
- 定时任务自动对账
- 支持手动触发对账
- 异常记录跟踪和处理

### 4. 重试机制
- 支付失败订单支持重试
- 批量扣款失败自动重试
- 对账异常自动或人工处理
